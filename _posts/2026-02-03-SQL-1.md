데이터베이스를 다루다 보면 숫자와 문자를 함께 연산하거나 결합해야 하는 상황을 자주 마주하게 됩니다. 이때 가장 중요한 개념이 바로 형변환(Type Casting)입니다.

이번 글에서는 묵시적(자동) 형변환과 명시적(수동) 형변환의 개념부터, 대표적인 연산(`'100' + 10`, `100 + '원'`)에서 DBMS별로 결과가 어떻게 달라지는지, 그리고 타 언어(파이썬, 자바)와의 철학 비교 및 실무에서 주의해야 할 함정까지 상세히 파헤쳐 보겠습니다.

---

## 1. SQL에서 숫자 + 문자 결합은 가능한가?

가능합니다 👍 다만 DBMS마다 방식이 조금씩 다르고, 거의 항상 형변환(Type Casting)이 관여합니다.

* **숫자 + 숫자** → 산술 덧셈
* **문자 + 문자** → 문자열 결합
* **숫자 + 문자** → ❌ 그대로는 안 되는 경우가 많고, 숫자를 문자로 변환한 뒤 결합해야 함

### DBMS별 문자열 결합 방식

1. **Oracle**
* Oracle에서는 `||`가 문자열 결합 연산자입니다.


```sql
SELECT 100 || '원' FROM dual;
-- 결과: '100원'

```


* 숫자는 자동으로 문자열로 형변환 됩니다. 다만 명시적으로 쓰면 더 안전합니다.


```sql
SELECT TO_CHAR(100) || '원' FROM dual;

```


2. **MySQL / MariaDB**
* MySQL은 `+`가 절대 문자열 결합이 아니며, 무조건 산술 연산입니다. ⚠️


```sql
SELECT 100 + '원';
-- 결과: 100 (문자는 0으로 취급)

```


* 문자열 결합은 `CONCAT()`을 사용해야 합니다.


```sql
SELECT CONCAT(100, '원');
-- 결과: '100원'

```


3. **PostgreSQL**
* Postgres는 꽤 엄격한 편입니다.


```sql
SELECT 100 || '원';
-- ❌ 오류 (타입 불일치)

```


* 명시적 형변환이 필요합니다.


```sql
SELECT 100::TEXT || '원';
-- 또는
SELECT CAST(100 AS TEXT) || '원';

```


4. **SQL Server (MSSQL)**
* SQL Server는 상황에 따라 자동 변환을 시도하지만 위험합니다.


```sql
SELECT 100 + '원';
-- ❌ 오류 발생 가능

```


* 권장 방식:


```sql
SELECT CAST(100 AS VARCHAR) + '원';
-- 또는
SELECT CONCAT(100, '원');

```



### 📌 요약 정리 표

| DB | 숫자 + 문자 가능 여부 | 방법 |
| --- | --- | --- |
| Oracle | ✅ | ` |
| MySQL | ❌ | `CONCAT()` |
| PostgreSQL | ❌ | `CAST`, `::TEXT` |
| SQL Server | ⚠️ | `CAST` 또는 `CONCAT()` |

---

이번엔 숫자 + 숫자도 파악해보자

마찬가지로 형변환을 자동 또는 수동으로 사용이 가능한데

* **자동 형변환** = 묵시적(암시적) 형변환 (`implicit conversion`)
* **수동 형변환** = 명시적 형변환 (`explicit conversion`)
→ `CAST()`, `CONVERT()` 같은 걸 직접 쓰는 경우

---

* **묵시적 형변환**
DBMS가 연산을 수행하기 위해 스스로 타입을 바꾸는 것
```sql
'100' + 10

```


→ DBMS가 `'100'`을 숫자로 바꿔서 계산할 수 있으면 `100 + 10`으로 해석
* **명시적 형변환**
개발자가 의도를 명확히 드러내는 것
```sql
CAST('100' AS INT) + 10

```


또는
```sql
TO_NUMBER('100') + 10

```



---

### 예제로 보는 DBMS별 차이 (중요)

#### 🔹 `'100' + 10`

| DBMS | 결과 | 설명 |
| --- | --- | --- |
| Oracle | **110** | 문자열 `'100'` → 숫자로 묵시적 변환 |
| MySQL | **110** | 문자열을 숫자로 변환 후 계산 |
| SQL Server | **110** | `VARCHAR` → `INT` 묵시적 변환 |
| PostgreSQL | ❌ **오류** | 암시적 변환 거의 안 해줌 |

* 📌 **PostgreSQL**
* `ERROR: operator does not exist: unknown + integer`
* → 반드시 명시적으로 써야 함


```sql
'100'::int + 10

```



---

### 즉 정리하자면

#### 🔹 `100 + '원'` (이건 분위기가 확 달라짐 😅)

| DBMS | 결과 | 설명 |
| --- | --- | --- |
| Oracle | ❌ **오류** | `'원'`을 숫자로 못 바꿈 |
| PostgreSQL | ❌ **오류** | 당연히 안 됨 |
| SQL Server | ❌ **오류** | 변환 불가 |
| MySQL | ⚠️ **100** | `'원'` → `0`으로 처리 |

* 📌 **MySQL의 특징**
```text
SELECT 100 + '원';  -- 결과: 100

```


* 숫자로 변환 불가능한 문자열 → `0`


## 2. 묵시적(자동) 형변환이 되는 DBMS 예시와 성향

### ① MySQL / MariaDB (성향: ⭐⭐⭐⭐)

* 자동 형변환을 매우 많이 합니다 (특히 문자 → 숫자).

```sql
SELECT 10 + '20';
-- 결과: 30
SELECT 10 + 'abc';
-- 결과: 10 ('abc' → 0으로 변환)

```

* **주의할 점:** `+`는 문자 결합이 아니며, 문자열이 숫자로 변환 불가능하면 `0`으로 처리하고 에러가 나지 않아 버그가 숨어들기 쉽습니다. (예: `SELECT '2024-01-01' + 1;` → `2025`)
* ➡️ MySQL은 “웬만하면 계산해줌” 스타일입니다.

### ② Oracle (성향: ⭐⭐⭐)

* 자동 형변환이 있지만 규칙이 명확합니다.

```sql
-- 숫자 → 문자
SELECT 100 || '원' FROM dual; -- 결과: '100원'

-- 문자 → 숫자
SELECT '100' + 20 FROM dual; -- 결과: 120
SELECT 'ABC' + 20 FROM dual; -- ❌ ORA-01722: invalid number

```

* ➡️ Oracle은 될 것 같으면 해주고 안 되면 바로 에러를 띄워 MySQL보다 훨씬 안전합니다.

### ③ SQL Server (MSSQL) (성향: ⭐⭐)

* 자동 형변환이 있긴 한데 예측이 어려우며, 우선순위 높은 타입으로 변환되거나 컬럼 타입에 따라 결과가 달라질 수 있어 실무에서는 거의 믿지 않고 `CAST`를 씁니다.

### ④ PostgreSQL (성향: ⭐ - 엄격)

* 자동 변환이 거의 없습니다.

```sql
SELECT 10 + '20'; -- ❌ 오류
SELECT 10 || '원'; -- ❌ 오류

```

* 반드시 명시해야 합니다 (`10::TEXT || '원'`, `10 + '20'::INT`). ➡️ “명확하지 않으면 안 해줌” 철학입니다.

## 3. MySQL에서 숫자를 문자로 취급하는가?

결론부터 말하면 **MySQL은 “상황에 따라” 숫자를 문자로도, 문자를 숫자로도 취급**하며, 그 기준은 연산자나 함수에 달려 있습니다.

### ① 숫자를 문자로 취급하는 경우 (문자열 컨텍스트)

* **`CONCAT()` 함수 사용 시:**
```sql
SELECT CONCAT(100, '원'); -- 결과: '100원'

```


숫자 `100`이 자동으로 문자열 `'100'`으로 변환됩니다. (`SELECT CONCAT(100, '원');`은 내부적으로 암시적 형변환에 해당합니다.)
* **문자열 함수 사용 시:**
```sql
SELECT LENGTH(100); -- 결과: 3
SELECT SUBSTRING(12345, 1, 2); -- 결과: '12'

```



### ② 숫자를 숫자로 취급하는 경우 (숫자 컨텍스트)

* **`+` 연산자 및 비교 연산:**
```sql
SELECT 100 + '원'; -- 결과: 100 ('원' → 0)
SELECT '10abc' + 5; -- 결과: 15 ('10abc' → 10)
SELECT '10' = 10; -- 결과: 1 (true)

```


* **컬럼 비교에서의 자동 형변환 (주의 ⚠️):**
```sql
-- col_int가 INT 타입인 경우
SELECT * FROM t WHERE col_int = '10';

```


`'10'`이 숫자 `10`으로 변환되지만, 인덱스 사용에 악영향을 주거나 데이터 정합성 문제를 유발할 수 있습니다.

## 4. 자동 형변환(묵시적) vs 수동 형변환(명시적) 차이

| 구분 | 자동 형변환 (묵시적) | 수동 형변환 (명시적) |
| --- | --- | --- |
| **누가 변환하는가** | DBMS | 개발자 |
| **가독성 / 작성법** | 짧고 편함 | 명확함 (`CAST`, `CONVERT`, `TO_CHAR` 등 직접 사용) |
| **안정성** | 낮음 (에러를 숨김) | 높음 (결과 예측 가능) |
| **DB별 차이** | 큼 | 거의 없음 |
| **실무 권장** | ❌ (지양) | ✅ (적극 권장) |

## 5. 파이썬과 자바에서는 형변환이 어떻게 이루어질까?

### ① 파이썬 (Python)

* **철학:** “애매하면 에러를 낸다.”
* SQL처럼 `10 + '20' → 30` 같은 암시적 형변환은 절대 안 해줍니다. 숫자 ↔ 숫자(`1 + 2.5`)나 `bool`과 `int` 연산 등 제한적인 수치 연산에서만 허용하고, 숫자와 문자열의 직접 연산은 무조건 `TypeError`를 발생시킵니다.

### ② 자바 (Java)

* **철학:** “안전한 방향(Widening)만 자동으로 해주고, 위험하면 컴파일 에러를 낸다.”
* `int`에서 `long`, `double`처럼 정보 손실 가능성이 없는 방향만 자동 형변환해주고, 문자열과의 연산이나 큰 타입에서 작은 타입으로의 대입은 철저히 막습니다.

## 6. 실무에서 형변환을 다룰 때 반드시 기억해야 할 점 📌

1. **문자열 결합은 전용 연산자/함수를 사용하세요.**
* 숫자를 문자와 이어 붙이고 싶다면 DBMS 공통으로 이식성이 좋은 `CONCAT()` 함수나 오라클/포스트그레스의 문자열 결합 연산자(`||`)를 사용해야 합니다. `+` 연산자는 데이터베이스에 따라 산술 연산이 될 수도 있어 혼란을 줍니다.


2. **자동 형변환에 기대지 말고 수동(명시적)으로 제어하세요.**
* 쿼리가 당장 대충 동작하더라도, 내부적으로 자동 형변환이 일어나면 **인덱스(Index)를 타지 못해 성능이 수십~수백 배 저하**되거나, 데이터 정합성이 깨지는 주원인이 됩니다.
* 타입을 맞추거나 `CAST()` / `CONVERT()`를 활용한 명시적 형변환을 습관화합시다.

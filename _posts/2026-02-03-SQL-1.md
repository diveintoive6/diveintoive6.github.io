데이터베이스를 다루다 보면 숫자와 문자를 함께 연산하거나 결합해야 하는 상황을 자주 마주하게 됩니다. 이때 가장 중요한 개념이 바로 **형변환(Type Casting)**입니다. 

이번 글에서는 묵시적(자동) 형변환과 명시적(수동) 형변환의 개념부터, 대표적인 연산(`'100' + 10`, `100 + '원'`)에서 DBMS별로 결과가 어떻게 달라지는지, 그리고 MySQL의 `CONCAT` 같은 함수 동작까지 상세히 파헤쳐 보겠습니다.

---

## 1. 묵시적 형변환 vs 명시적 형변환 개념 비교

### 🔹 묵시적 형변환 (Implicit Type Casting / 자동 형변환)
* 개발자가 별도의 변환 코드를 작성하지 않아도, DBMS가 문맥을 파악해 **알아서 타입을 바꿔주는 것**입니다.
* **장점:** 쿼리가 짧고 작성이 편리합니다.
* **단점:** DBMS마다 규칙이 제각각이고, 잘못된 연산에서도 에러를 뱉지 않고 조용히 넘어가 치명적인 버그를 유발할 수 있습니다. (예: 인덱스 누락, 데이터 유실)

### 🔹 명시적 형변환 (Explicit Type Casting / 수동 형변환)
* 개발자가 `CAST`, `CONVERT`, `TO_CHAR` 등의 함수를 사용해 **직접 타입을 지정해 주는 것**입니다.
* **장점:** 결과가 예측 가능하고, 에러를 빠르게 발견할 수 있으며 DB 이식성과 성능(인덱스 활용) 측면에서 훨씬 안전합니다.
* **단점:** 코드가 조금 길어지고 번거롭지만, **실무에서는 언제나 명시적 형변환을 습관화하는 것이 베스트 프랙티스**입니다.

## 2. 묵시적 형변환의 위험성: DBMS별 연산 결과 비교

숫자 문자 결합이나 산술 연산 시, 대표적인 두 가지 케이스(`'100' + 10`과 `100 + '원'`)에서 각 DBMS가 어떻게 반응하는지 살펴보겠습니다.

### 📌 케이스 1: `SELECT '100' + 10;` (문자열 숫자 + 숫자)

* **MySQL / MariaDB**
  * 결과: `110` (자동으로 문자를 숫자로 변환하여 산술 덧셈 수행)
  * 특징: 숫자로 변환할 수 없는 문자(`'abc' + 10`)가 들어가면 에러 없이 `0`으로 처리해 버리기 때문에 버그를 찾기 어려울 수 있습니다.
* **Oracle**
  * 결과: `120` (숫자 우선 규칙에 따라 `'100'`을 숫자로 변환해 계산)
  * 특징: 변환이 불가능한 문자열이면 명시적으로 `ORA-01722: invalid number` 에러를 띄워 안전합니다.
* **SQL Server (MSSQL)**
  * 결과: `110` (상황에 맞게 자동 변환 시도)
* **PostgreSQL**
  * 결과: ❌ 오류 발생 (`operator does not exist: integer + unknown` 등 타입 불일치 에러)
  * 특징: 매우 엄격하여 묵시적 변환을 거의 허용하지 않습니다. (`'100'::INT + 10`처럼 명시해야 함)

---

### 📌 케이스 2: `SELECT 100 + '원';` (숫자 + 문자)

* **MySQL / MariaDB**
  * 결과: `100` (플러스(`+`) 연산자는 무조건 산술 연산이므로, `'원'`은 숫자로 바꿀 수 없어 `0`으로 취급되어 `100 + 0 = 100`이 됨)
  * ⚠️ **주의:** MySQL에서 `+`는 절대 문자열 결합용이 아닙니다!
* **Oracle**
  * 결과: ❌ 오류 발생 (`ORA-01722: invalid number` - `'원'`을 숫자로 바꿀 수 없기 때문)
* **SQL Server (MSSQL)**
  * 결과: ❌ 변환 오류 발생
* **PostgreSQL**
  * 결과: ❌ 타입 불일치 오류 발생

## 3. MySQL에서의 문자열 컨텍스트와 `CONCAT()`

MySQL에서 `SELECT CONCAT(100, '원');`을 실행하면 결과는 `'100원'`이 나옵니다. 

* **이게 자동 형변환인가요?**
  * 네, 그렇습니다. `CONCAT()` 함수는 문자열을 인자로 받기 때문에, 내부적으로 숫자 `100`을 문자열 `'100'`으로 변환하는 **묵시적 형변환**이 일어난 것입니다.
* **`+` 연산자와의 차이**
  * `+` 연산자는 숫자 컨텍스트를 요구하여 문자를 숫자로 바꾸려 하거나 에러를 내지만, `CONCAT`이나 문자열 관련 함수들은 숫자 컨텍스트를 문자열로 전환하는 성향을 가집니다. 이처럼 연산자나 함수가 무엇을 요구하느냐에 따라 MySQL의 타입 취급 방식이 달라집니다.

## 4. 요약 및 DBMS별 성향 비교 표

| DBMS | 자동 형변환 성향 | `'100' + 10` 결과 | `100 + '원'` 결과 | 특징 및 실무 시사점 |
| :--- | :--- | :--- | :--- | :--- |
| **MySQL** | 높음 (관대함) | `110` | `100` (`'원'`을 0으로 처리) | 에러를 잘 안 내고 0으로 처리해 버려 버그가 숨기 쉬움 |
| **Oracle** | 보통 (규칙적) | `120` | 에러 발생 | 실패 시 명확한 에러 반환 (`ORA-01722`) |
| **SQL Server** | 보통 | `110` | 에러 발생 | 상황에 따라 변환 시도 |
| **PostgreSQL** | 낮음 (매우 엄격) | 에러 발생 | 에러 발생 | 묵시적 변환 거의 없음. 명시적 변환(`CAST`) 필수 |

---

## 5. 실무 개발 베스트 프랙티스 💡

1. **`+` 연산자는 오직 숫자 계산에만 사용하세요.** 
   * 문자열을 이어 붙이고 싶다면 DBMS 공통으로 이식성이 좋은 `CONCAT()` 함수나 오라클/포스트그레스의 문자열 결합 연산자(`||`)를 사용해야 합니다.
2. **자동 형변환에 기대지 말고 수동(명시적)으로 제어하세요.** 
   * 쿼리가 당장 대충 동작하더라도, 내부적으로 자동 형변환이 일어나면 **인덱스(Index)를 타지 못해 성능이 수십~수백 배 저하**되거나, 데이터 정합성이 깨지는 주원인이 됩니다. 
   * 타입을 맞추거나 `CAST()` / `CONVERT()`를 활용한 명시적 형변환을 습관화합시다.
